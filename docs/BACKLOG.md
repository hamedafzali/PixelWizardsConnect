# Backlog — deferred items

Items intentionally deferred out of the task that surfaced them, tagged by the
`docs/ADR-001-architecture.md` phase they belong to.

| Item | Why deferred | Phase |
|---|---|---|
| `TcpTransport.ReceiveLoop` invokes `MessageReceived` synchronously, so its catch/break wraps every downstream handler — a rendering NRE is indistinguishable from a corrupt frame, and both kill the session. Transport errors and handler errors are different failure classes. | Needs the Session/transport boundary to exist | 2 |
| Viewer UI may not surface a sensible message on the deserialize-failure disconnect path | UX question, no owner yet | 5 |
| `ScreenChangeDetector` (System.Drawing) and `SkiaScreenChangeDetector` (SkiaSharp) are near-duplicate algorithms in two implementations, plus a third byte-identical copy of the Skia one (`PixelWizard.AvaloniaClient.Platform.Mac.SkiaScreenChangeDetector` vs `PixelWizard.LinuxHost.SkiaScreenChangeDetector`) | Consolidation is only safe once all are under an identical assertion suite (T2, `tests/PixelWizard.Tests/ScreenChangeDetector/`) | 3 |
| T2's `ScreenChangeDetectorAssertionSuite` has not been run against `PixelWizard.WindowsHost.ScreenChangeDetector` on real Windows — only cross-compiled and code-reviewed line-by-line against the Skia implementation. No disagreement has been found by inspection (block size, threshold, sampling step, and merge-margin constants all match), but this is unverified empirically. | Needs T4's `windows-latest` CI job to actually execute `SystemDrawingScreenChangeDetectorTests` | 3/4 |
| `router-server` `handleConnect` never checks `codeTTL` itself — expiry is enforced only by the periodic `cleanupExpiredHosts` sweep (default every 5 min). A code past its 30-min TTL but not yet swept still connects successfully via `/connect`. Worst case: a code stays usable up to `codeTTL + cleanupInterval` after it should have expired. Pinned as current behaviour in `router-server/main_test.go` (`TestHandleConnect_ExpiredCode_NotEnforcedAtConnectTime`); not fixed. | Out of scope for T3 (pin-only); fixing requires `handleConnect` itself to check TTL at lookup time | 0 |
| `router-server` `handleRegister` performs no validation of required fields — an empty `hostId`/`hostName` is silently accepted (200) and stored under the `""` key in the `hosts` map, where multiple empty-`hostId` registrations would collide/overwrite each other (though each still gets a distinct `hostsByCode` entry). Pinned as current behaviour in `TestHandleRegister_EmptyFields_AcceptedWithoutValidation`; not fixed. | Out of scope for T3 (pin-only) | 0 |
| T5 added TLS certificate pinning: a fingerprint mismatch throws `CertificatePinMismatchException`, but no UI surfaces it to the user — the viewer currently only wires generic `TcpTransport.Error` handling. The user needs a distinct "possible MITM, refused" dialog, separate from a generic "host offline" message, plus a UI-reachable way to call `TcpTransport.ForgetPin`. | UX/presentation, needs the Session/UI boundary from item above | 2/5 |
| T5's TOFU pinning cannot protect the very first connection to a host — an attacker on-path at initial pin time is trusted permanently. The router already has an authenticated channel to both the host and the viewer and could convey the host's expected certificate fingerprint out-of-band at registration/connect time, closing the first-connection gap for router-mediated sessions (direct-IP LAN connections would still lack this). | Needs router protocol changes; direct-connect fallback still needed | 3 |

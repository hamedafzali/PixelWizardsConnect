# Backlog — deferred items

Items intentionally deferred out of the task that surfaced them, tagged by the
`docs/ADR-001-architecture.md` phase they belong to.

| Item | Why deferred | Phase |
|---|---|---|
| `TcpTransport.ReceiveLoop` invokes `MessageReceived` synchronously, so its catch/break wraps every downstream handler — a rendering NRE is indistinguishable from a corrupt frame, and both kill the session. Transport errors and handler errors are different failure classes. | Needs the Session/transport boundary to exist | 2 |
| Viewer UI may not surface a sensible message on the deserialize-failure disconnect path | UX question, no owner yet | 5 |
| `ScreenChangeDetector` (System.Drawing) and `SkiaScreenChangeDetector` (SkiaSharp) are near-duplicate algorithms in two implementations, plus a third byte-identical copy of the Skia one (`PixelWizard.MacHost.SkiaScreenChangeDetector` (moved there by T11) vs `PixelWizard.LinuxHost.SkiaScreenChangeDetector`) | Consolidation is only safe once all are under an identical assertion suite (T2, `tests/PixelWizard.Tests/ScreenChangeDetector/`) | 3 |
| T2's `ScreenChangeDetectorAssertionSuite` has not been run against `PixelWizard.WindowsHost.ScreenChangeDetector` on real Windows — only cross-compiled and code-reviewed line-by-line against the Skia implementation. No disagreement has been found by inspection (block size, threshold, sampling step, and merge-margin constants all match), but this is unverified empirically. | Needs T4's `windows-latest` CI job to actually execute `SystemDrawingScreenChangeDetectorTests` | 3/4 |
| T5's TOFU pinning cannot protect the very first connection to a host — an attacker on-path at initial pin time is trusted permanently. The router already has an authenticated channel to both the host and the viewer and could convey the host's expected certificate fingerprint out-of-band at registration/connect time, closing the first-connection gap for router-mediated sessions (direct-IP LAN connections would still lack this). | Needs router protocol changes; direct-connect fallback still needed | 3 |
| T3's `HandlerError` currently goes to `Debug.WriteLine` only, so handler bugs are invisible in release builds unless they hit the 5-consecutive escalation. Before T3, a handler bug killed the session — visible and diagnosable. Now the single-failure case, which is the common one, is silently swallowed. "Report and continue" needs somewhere for the report to actually go: a log file, a session diagnostics panel, or crash reporting. This is a deliberate consequence of T3, not an oversight. | Needs an actual observability sink (log file / diagnostics panel / crash reporting), none of which exist yet | 7 |
| T6 renamed `PixelWizard.Transport` to `PixelWizard.Transport.Tcp`, but `NetworkDiscovery.cs` (UDP LAN discovery) and `RouterHttpClient.cs` (HTTP client to the router) are neither TCP-transport-specific nor WebSocket-specific, and the plan's six-project target shape has no assigned home for them. They stayed in `Transport.Tcp` for now, which means the project won't actually be narrow even after T7 removes `WebSocketHostServer.cs`. **Decided at T8:** target project is `PixelWizard.Signaling` — both classes are connection-establishment (finding a peer, negotiating a route), not transport, and that's exactly the category ADR-001's Phase 3 expands when the router becomes persistent WebSocket signaling (SDP/ICE exchange, TURN credential issuance). Moving them now, in Phase 2, would extract them into a shape Phase 3 immediately rewrites out from under — a second move instead of one. Scheduled for Phase 3's kickoff, before the SDP/ICE work starts, so Phase 3 doesn't inherit orphaned classes and doesn't do a redundant move-then-redesign either. | Needs Phase 3's router/signaling work to define the real API shape first | 3 |
| Go router's `router-server` package has a genuine data race in host registration/cleanup: `TestRegistrationRacingCleanup` under `-race` failed once on CI run 34748369785 (T9.2a's push), then passed on the identical code on rerun and on every prior run on this branch and on `main`. Intermittent, not a regression from T9.2a (that commit touches zero `.go` files) — the race is real but narrow enough that `-race` only catches it sometimes. | Needs someone to actually read `router-server`'s registration/cleanup path for the unsynchronized access `-race` is flagging; not yet root-caused | 3 |
| Found by reading T9.3b's code, **not reproduced**: `StartDirectHost`/`RegisterWithRouter` `await` the first listen, and `TcpTransport.StartServerAsync` only completes once a viewer connects. So everything after it (`_captureLoop.Start()`, `NetworkDiscovery.AnnounceAsync`, the "Host ready. Viewer address: …" / "Listening — tell viewer to connect…" statuses) appears to wait for the first viewer, which would leave the status at "Starting host…" and keep LAN discovery from ever announcing a host that is still waiting. Needs a manual run to confirm before fixing. | Unconfirmed; a behaviour change, not a move | 2 |
| Found at T10, **reproduced**: `TcpTransport.ConnectAsync` awaits `SslStream.AuthenticateAsClientAsync` with no timeout or cancellation. If the viewer uses TLS and the host is listening in plaintext (the host's TLS checkbox off), the host never answers the ClientHello and the viewer hangs in `ConnectAsync` indefinitely. T10's negative control (TLS viewer against a plaintext `HostListener`) hung until killed instead of failing. In the app this presumably leaves the viewer stuck at "Connecting…"; not checked in the UI. | A behaviour change (connect timeout + a user-facing message), not a move | 2/5 |
| Found at T12: "Trust new certificate" only forgets the old pin, and the next connect pins whatever certificate the host presents *then* (plain TOFU), not the fingerprint the user was just shown. An attacker who can swap certificates between the two connects would get trusted. Pinning the displayed fingerprint directly needs a new `TcpTransport` API (replace pin with a given value), which the plan's "no TOFU-pinning redesign" rule kept out of T12. | Transport API change, out of T12's scope | 3 |
| Found at T12 by reading: `TcpTransport.ConnectAsync` swallows connect failures into `Error` + `Disconnect`, and MainViewModel ignores `Error` while not connected, so a refused/unreachable host shows only "Disconnected". `FriendlyError`'s `SocketException` messages ("No host is accepting connections…") are unreachable on the viewer connect path. T12 fixed this for certificate failures only. | UX behaviour change beyond T12 | 2/5 |
